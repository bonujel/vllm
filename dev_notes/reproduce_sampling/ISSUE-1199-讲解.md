# Issue #1199 讲解：可复现采样 / 推理验证（入门版）

> 这份文档面向没接触过这块的人，从零讲清楚这个任务在干嘛、代码到了哪一步、有哪些问题。
> 每个结论都配了真实代码或运行结果。运行环境：Python 3.10.12，纯 CPU，无 GPU。
> 对应 issue：https://github.com/gonka-ai/gonka/issues/1199

## 〇、先说这个任务是干嘛的

一句话：**审查一套"防作弊验证"的半成品代码，找漏洞，判断能不能安全上线，写一份报告。**

注意：这**不是让你写新功能**，是让你当审查员。issue 原文：

> "This task is not primarily about writing new code... check for vulnerabilities, and define how to introduce it softly."

---

## 一、背景：要防的是什么作弊

gonka 是一个**去中心化的 AI 推理网络**：

- 有人想跑一个很贵的大模型（比如 Qwen3-235B），自己没那么强的显卡。
- 网络里的**执行者（executor）**说"我有大显卡，我帮你跑，给我钱"。
- 跑完把结果交回来，拿报酬。

**问题**：执行者会不会撒谎？他**声称**用了贵模型，**实际**偷偷用便宜的小模型（Qwen2.5-3B），省下的显卡钱自己赚。输出看着差不多，但是劣质货。

> 类比：你雇装修队，合同写"用进口大理石"，工人偷偷贴便宜瓷砖，钱照收。

所以需要一个**验证者（validator）**来抽查：你交回来的结果，**真是那个贵模型生成的吗？**

---

## 二、为什么验证很难

你可能会想：验证者自己再跑一遍，对比结果不就行了？

**难点在于 AI 生成有随机性。** 大模型每生成一个词，不是选"唯一正确答案"，而是给出一张**概率表**，再从里面**掷骰子**抽一个：

```
"今天天气很___"  →  { 好: 60%, 热: 25%, 糟: 10%, 蓝: 5% }
```

同样的输入跑两次，可能抽到不同的词。所以验证者重跑一遍，句子跟执行者的对不上，**这很正常**，没法直接比。

怎么办？——**两阶段验证**。

---

## 三、两阶段验证（整个方案的核心）

### Stage 2：分布检查（已经有了，gonka 里是 Go 写的）

不比"选了哪个词"，而是比"**那张概率表**长得对不对"。

- 执行者每生成一个词，都附带交出当时那张概率表（这叫 **artifact / 证物**）。
- 验证者用真模型重算概率表，跟执行者交的对比：接近 → 通过；差太多 → 撒谎。

因为便宜模型算出来的概率表，和贵模型的不一样。

### 漏洞：Pre-fill 攻击

但 Stage 2 有个洞。作弊者可以这样钻：

1. 先用**便宜模型**生成一句话（省钱）。
2. 再把这句**已经定死的话**喂给**贵模型**，只让它**算一次概率表**（不让它掷骰子选词）。
3. 提交："贵模型的概率表 + 便宜模型选的词"。

结果：概率表是真的（能过 Stage 2），但**句子其实是便宜模型造的**。

> 类比：让学霸只在你写好的答案旁"标注正确率"，但答案是你自己瞎写的。老师只看了正确率标注，没发现答案是假的。

### Stage 1：序列检查（issue #1199 要审查的东西）

为了堵这个洞，加一个前置检查：**强制"掷骰子"这一步也变得可复现、可验证。**

做法：
1. 不用真随机骰子，用一个**公开种子（seed）**造一个"伪随机骰子"（叫 RNG）。这种骰子**给同样的种子，每次掷出的点数完全一样**。
2. 执行者生成每个词：模型给概率表 → 用这个骰子从表里抽词。
3. 验证者**重放骰子**："把你交的概率表 + 公开种子给我，我自己掷一遍。你选的词如果**正好是骰子该选的那个** → 你没作弊；对不上 → 撒谎。"

**为什么能堵住 pre-fill？** 因为现在要求"每个词都必须是骰子从模型概率表里抽出来的"。作弊者用便宜模型预先造的句子，拿去重放骰子时**对不上**——骰子会指向别的词。

**两阶段连起来跑**：先 Stage 1（便宜，纯 CPU，不过就直接拒）→ 过了再 Stage 2（贵，要 GPU）→ 最终接受/拒绝。

---

## 四、为什么"可复现"工程上这么难（关键难点）

要命的地方：**骰子必须在执行者和验证者两台不同机器上，掷出 bit 级别完全一样的点数。**

但骰子的输入是"概率"，而概率是**浮点数**。浮点数有个特性：

> 同一个计算，在不同 GPU / 驱动 / 库版本上，算出来的末几位可能不一样。

差一丁点，骰子落在概率表边界上的选择就可能翻——本来选 A，差一点点变成选 B。于是验证者重放时跟执行者对不上，**好人被误判成作弊者（false reject / 误拒）**。这是灾难。

解决思路：不用浮点掷骰子，改用 **SHA256 当骰子 + 整数运算**。整数在任何机器上都 bit 一致，没有浮点漂移。这也是后面"两条分支"分歧的根源。

---

## 五、代码现状：有两条分支，别搞混

这是最容易懵的地方。同一个功能有**两套代码**，做法不一样：

| | `v011` 分支 | `dump` 分支（现在在这条） |
|---|---|---|
| 怎么掷骰子 | **浮点**：GPU 算概率，会漂移 | **整数**：decimal 管线，不漂移 |
| 接进系统了吗 | 接了一半（有开关、有采样器） | 几乎没接（只有算法核 + 文档） |
| 时间 | 2025-12 ~ 2026-02 | 2026-04 |

有意思的是：**v011 作者自己就知道浮点不行**——他在代码注释里写了"整数是为了跨语言可复现，因为浮点有舍入差异"，还预留了整数函数。`dump` 就是把整数方案扶正，但把集成删了。**两条分支一直没合并。**

记住这句话："**两条分支、各残一半、没合并**"——后面全靠它。

## 六、逐个问题讲解（配代码和运行结果）

### 问题 1：骰子（RNG）本身对不对？—— 对的

我在纯 CPU 上实跑了核心模块，输出：

```
iter_u64("reference_seed_v1", 5)[0]   = 4286832458236889005
decimal_sample(seed="42|[1,2,3]") x2  = 791 791      ← 同种子两次都抽到 791
sum(logprobs_to_weights(...))         = 65536         ← 整数权重和精确=2^16
```

**这证明骰子是确定性的**：同种子必得同结果，整数运算精确。这部分没问题，是好的。（第一个数 `4286832458236889005` 将来 Go 版必须 bit 级对上。）

### 问题 2：种子（seed）安全吗？—— 不安全（致命漏洞）

先看提案要求种子怎么配：
```
种子 = SHA256(用户种子 + 链上推理ID)
```
关键是**链上推理ID**——区块链发的，作弊者改不了。

再看代码实际怎么配（`docs/DETERMINISTIC_SAMPLING_VALIDATION.md:498`）：
```
种子 = 用户种子 | prompt的token
```
它把"链上推理ID"换成了"prompt的token"，而 prompt 的 token 是**作弊者能控制的**。

**后果：离线枚举攻击（offline grinding）。** 作弊者可以在自己电脑上**反复换种子试**：
> 用便宜模型编好一句假话 → 不停换种子重放骰子 → 试个几千上万次，总能撞到一个种子，让这句假话恰好通过序列检查 → 提交这个种子。

> 类比：本该用"银行发的、你改不了的验证码"，代码却改用"你自己能填的那个数"。等于让作弊者自己带骰子、还能私下先掷一万遍挑个顺眼的——验证就废了。

**这是 blocker（阻断项，不修不能上线）。** 修法：种子必须由协议强制、含作弊者选不了的成分，比如 `H(prompt哈希 + 推理ID + 执行者地址 + 起始区块哈希)`。

### 问题 3：证物（artifact）内容够吗？—— 不够，还有个 blocker

提案要求证物含"每个位置的 top-k 词 **及其概率**"。但看装证物的真代码（`vllm/validation.py:13`）：

```python
class EnforcedToken(BaseModel):
    token: str
    top_tokens: List[str] = Field(default_factory=list)   # 只有词的名字——没有概率！
```

**只有词，没有概率数字。**

**更麻烦的是"概率怎么写成字符串"没定规矩（第二个 blocker）。** 同一个数 `-0.05`：
```
repr(-0.05)                  = "-0.05"
float32(-0.05) 加宽到 f64    = "-0.05000000074505806"
```
两个都"对"，取决于从哪个浮点出发。而且 **Python 和 Go 把浮点转字符串的规则天生不一样**（golang/go#17997）。执行者用 Python、验证者可能用 Go——字符串对不上，好人被误判。

修法：证物必须存模型实际输出的那个浮点值，用**唯一约定**的方式转字符串，且**只在 vLLM 侧转，Go 永不碰浮点格式化**。

### 问题 4：整体做到哪一步了？—— 两半都没接进系统

看 v011 的真代码，一眼看出它走浮点（`deterministic_sampler.py`）：
```python
# 计算 softmax 概率
probs = logits.softmax(dim=-1, dtype=torch.float32)   # GPU float32——换台机器就会变
...
token_id = sample_categorical(probs_cpu[i], rng)      # 在浮点上掷骰子
```

还有个关键事实——采样器**根本没被真正调用**。实跑 `git grep`：
```
$ git grep -l DeterministicSampler origin/tg/deterministic_sampling_v011
vllm/v1/sample/deterministic_sampler.py        ← 它自己
tests/v1/sample/test_deterministic_sampler.py  ← 一个测试
```
只被自己和一个测试引用——真正干活的 `gpu_model_runner` 从没调用它。**也就是说，这套东西压根没接进真实推理流程。**

而验证者那边的重放代码，本该在一个叫 `validation_sampling.py` 的文件里，但**两条分支上都没有这个文件**。

盘点：
- **已有**：整数算法核（dump）、浮点采样器 + 接线骨架（v011）、设计文档。
- **要改**：把浮点采样换成整数、改种子、修测试。
- **要新建**：让 worker 真正调用采样器、验证端重放、防枚举的种子、浮点→字符串规范、Go 参考实现。

### 问题 5：能不能先"软上线"（只记录不惩罚）？—— 现在不行

log-only 至少要求采样器在真实生成时被调用。但问题 4 已经证明——**采样器没被调用**。所以现在没有任何东西能 log-only 跑。

能现在安全纳入的，只有独立、不碰线上请求的部分（算法核、离线对拍工具）。其余全得等。

### 问题 6：还有哪些雷？

- **greedy 模式绕过骰子**：真代码里，当 `temperature < 0.00001`（近似 0）时走 `argmax`（直接取最大），**完全跳过骰子**。意味着 temperature=0 时这套验证毫无防护，作弊照样钻。
- **测试跑不起来**：测试 import 了 `sample_categorical`、`WeightedPrefixSampler`，但这俩在 `dump` 核里不存在（它们在 v011）。所以测试一跑就报错，**"测试通过"不能当证据**。
- **没有 Go 实现**：嘴上说"Python 和 Go 结果一致"，但 Go 那一半根本不存在，**从没实测过**。
- **一堆已知限制**：logit_bias 被禁、top_k 被截、只能用 CPython、中间任何代理/日志截断浮点精度都会让验证失败。

---

## 七、最终结论

把上面串起来：

| 问题 | 性质 |
|---|---|
| 种子可被离线枚举 | 🔴 blocker（安全洞） |
| 浮点→字符串没规范 | 🔴 blocker（跨语言对不上） |
| 采样器没接进 worker | 高（连 log-only 都跑不起来） |
| 没有 Go 实现 | 高（核心主张没法验） |
| greedy 绕过、测试跑不起来 | 中/低 |

任意一条都够呛，叠一起 → **最终结论：not ready（没准备好）。**

issue 里说"软上线风险低"——那只是因为**现在啥都还没接线**。真接上之前，这两个 blocker 和集成都必须先搞定。

**推进顺序建议**：① 定架构（走整数路线）→ ② 把两条分支合并（保留 v011 骨架、换上整数管线）→ ③ 堵两个 blocker（协议强制种子 + 唯一的浮点→字符串规范）→ ④ 补 Go 实现和对拍向量 → ⑤ 再 log-only 上线、测误拒率 → ⑥ 达标才转强制。
